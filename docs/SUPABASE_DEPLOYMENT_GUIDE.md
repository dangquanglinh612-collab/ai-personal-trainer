## 0. 先确定要部署的是什么

Supabase 不是 Streamlit 的页面托管平台。推荐的完整架构是：

```text
教练浏览器
    │ HTTPS
    ▼
Streamlit Community Cloud / Render / Railway（运行 fitness.py）
    │ 以每位已登录教练的 Supabase Auth 会话访问
    ├──────────────► Supabase Auth（教练账号）
    ├──────────────► Supabase Postgres（业务数据）
    └──────────────► Supabase Storage（私有训练照片）
```

对于这个项目，建议使用：

- Supabase：Postgres + Auth + Storage。
- Streamlit Community Cloud：最省事的应用托管方式；如果需要中国大陆网络、固定区域、私有网络或更细的运维控制，改用 Render/Railway/自有服务器。
- GitHub：保存代码和触发应用重新部署。

这样解决了目前本地 SQLite 无法在多设备间同步、云端文件系统不持久、训练照片不能安全共享的问题。

## 1. 迁移前必须完成的安全准备

### 1.1 备份与冻结写入

1. 在本机完整复制项目目录，尤其是：
   - `ai_coach_os.db`
   - `fitness_coach.db`（若仍有旧数据）
   - `uploads/`（如果存在）
   - `assets/`
2. 用当前程序打开备份，确认会员、训练记录和照片均可读取。
3. 选一个迁移窗口。在导出后不要继续向旧系统写入数据；否则导出和上线之间的数据会遗漏。
4. 先在 Supabase **新建测试项目**跑通全过程，再对正式项目执行一次。不要用生产项目边试边改。

### 1.2 立刻处理旧的账号模型

当前 `coaches.password` 保存的是明文密码，并且代码还会创建 `wenwen / 123456` 与 `numb / 123456`。这些账号和密码不能原样上线。

迁移目标应改为 Supabase Auth 的“邮箱 + 密码”账号：

- 每位教练先提供真实、可收信的邮箱。
- 为每人创建 Auth 用户，或让教练通过注册页自行设置新密码。
- 不再保留、展示或导入旧的明文密码。
- 正式环境关闭公开注册，只允许管理员邀请教练。

如果现有用户没有邮箱，先收集邮箱后再迁移。不要用虚假的占位邮箱作为长期登录方式。

### 1.3 不提交机密与本地数据

在 Git 仓库的 `.gitignore` 中至少确保有：

```gitignore
.streamlit/secrets.toml
*.db
uploads/
__pycache__/
```

绝不能把 Supabase 的 secret/service key、数据库密码、AI API key 或真实会员数据提交到 GitHub。

## 2. 创建 Supabase 项目

1. 打开 [Supabase Dashboard](https://supabase.com/dashboard)，创建一个组织和一个项目。
2. 区域选择离主要教练和用户最近、且满足数据合规要求的区域；创建后不应依赖随意换区。
3. 设置一个高强度数据库密码，并保存到密码管理器。
4. 等项目初始化完成后，进入 **Project Settings → API**，记录：
   - Project URL
   - Publishable key（较旧项目可能标为 anon key）
   - Secret key（较旧项目可能标为 service_role key）
5. Publishable key 可以随应用使用，但不能替代访问控制；Secret key 只能用于一次性本机迁移脚本或受信任的后端管理任务，绝不能发给浏览器、写进代码或贴到截图中。

Supabase 的 Python 客户端以 `create_client(url, key)` 初始化；官方参考见 [Python client 初始化文档](https://supabase.com/docs/reference/python/initializing)。

## 3. 建库：在 SQL Editor 一次性执行以下脚本

在 Supabase Dashboard 中进入 **SQL Editor → New query**，粘贴并执行本节全部 SQL。它为当前 SQLite 的 11 张业务表建立 PostgreSQL 版本，并把每条数据都归属到一个 Supabase Auth 用户。

> 执行前请确认这是测试/新项目。生产环境的 schema 变更应保存为版本化 SQL migration 后再执行。

  id uuid primary key references auth.users(id) on delete cascade,
  username text unique not null,
  nickname text not null default '',
  created_at timestamptz not null default now()
);

-- Auth 新用户生成相应 profile。
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer set search_path = public
as $$
begin
  insert into public.profiles (id, username, nickname)
  values (
    new.id,
    coalesce(nullif(new.raw_user_meta_data ->> 'username', ''), new.id::text),
    coalesce(new.raw_user_meta_data ->> 'nickname', '')
  );
  return new;
end;
$$;

### 3.3 Row Level Security（RLS）

继续在 SQL Editor 执行下面脚本。RLS 保证教练只能读取、插入、修改或删除自己名下的会员和记录。即使前端某处漏传筛选条件，也不会把另一位教练的数据直接返回。

```sql
-- 开启 RLS。
alter table public.profiles enable row level security;
alter table public.members enable row level security;
alter table public.training_logs enable row level security;
alter table public.lesson_plans enable row level security;
alter table public.exercise_library enable row level security;
alter table public.training_sessions enable row level security;
alter table public.body_measurements enable row level security;
alter table public.training_session_photos enable row level security;
alter table public.training_session_exercises enable row level security;
alter table public.ai_analysis_reports enable row level security;
alter table public.training_plans enable row level security;
alter table public.training_plan_exercises enable row level security;

create policy "read own profile" on public.profiles
  for select to authenticated using ((select auth.uid()) = id);
create policy "update own profile" on public.profiles
  for update to authenticated using ((select auth.uid()) = id)
  with check ((select auth.uid()) = id);

-- 所有直接带 coach_id 的表共享同一条所有权规则。
create policy "members owned by coach" on public.members for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "training logs owned by coach" on public.training_logs for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "lesson plans owned by coach" on public.lesson_plans for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "training sessions owned by coach" on public.training_sessions for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "measurements owned by coach" on public.body_measurements for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "session photos owned by coach" on public.training_session_photos for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "AI reports owned by coach" on public.ai_analysis_reports for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);
create policy "training plans owned by coach" on public.training_plans for all to authenticated
  using ((select auth.uid()) = coach_id) with check ((select auth.uid()) = coach_id);

-- 这两张子表没有 coach_id；通过父记录验证所属教练。
create policy "session exercises owned through session"
  on public.training_session_exercises for all to authenticated
  using (
    exists (
      select 1 from public.training_sessions s
      where s.id = session_id and s.coach_id = (select auth.uid())
    )
  )
  with check (
    exists (
      select 1 from public.training_sessions s
      where s.id = session_id and s.coach_id = (select auth.uid())
    )
  );

create policy "plan exercises owned through plan"
  on public.training_plan_exercises for all to authenticated
  using (
    exists (
      select 1 from public.training_plans p
      where p.id = plan_id and p.coach_id = (select auth.uid())
    )
  )
  with check (
    exists (
      select 1 from public.training_plans p
      where p.id = plan_id and p.coach_id = (select auth.uid())
    )
  );

-- 动作库只允许已登录教练读取；初始数据由受信任的迁移脚本写入。
create policy "authenticated coaches can read exercises"
  on public.exercise_library for select to authenticated using (true);
```

RLS policy 里的 `auth.uid()` 取自登录用户的 JWT。官方的 [RLS 指南](https://supabase.com/docs/guides/database/postgres/row-level-security) 也特别说明：`UPDATE` 需要相应的 `SELECT` 策略；上面的 `for all` 已覆盖此要求。

## 4. 配置私有训练照片 Storage

1. 在 Dashboard 打开 **Storage → New bucket**。
2. Bucket 名称填 `training-photos`。
3. **不要**勾选 Public bucket。
4. 在 Bucket 设置限制：
   - Allowed MIME types：`image/jpeg,image/png`
   - 单文件大小：按业务需要，例如 10 MB。
5. 在 SQL Editor 执行以下 Storage 对象规则：

```sql
create policy "coach reads own training photos"
on storage.objects for select to authenticated
using (
  bucket_id = 'training-photos'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);

create policy "coach uploads own training photos"
on storage.objects for insert to authenticated
with check (
  bucket_id = 'training-photos'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);

create policy "coach deletes own training photos"
on storage.objects for delete to authenticated
using (
  bucket_id = 'training-photos'
  and (storage.foldername(name))[1] = (select auth.uid()::text)
);
```

对象路径统一采用：

```text
{coach_uuid}/{member_id}/{session_id}/{uuid}.jpg
```

数据库只保存这个 `object_path`，不要保存本机 `uploads/.../` 路径，也不要把图片二进制放进 PostgreSQL。私有 Bucket 的图片展示时使用短时效 signed URL。Storage 默认不允许上传，必须用 `storage.objects` 的 RLS policy 放行；详见 [Storage Access Control](https://supabase.com/docs/guides/storage/security/access-control)。

## 5. 将 Streamlit 代码从 SQLite 改为 Supabase

这一步不是把 `DB_NAME` 改成一个 URL 就能完成。SQLite 的 `cursor.execute(...)`、`lastrowid`、本地事务和文件写入都必须替换。

### 5.1 依赖与本地 secrets

在仓库根目录新增 `requirements.txt`：

```text
streamlit>=1.40,<2
supabase>=2,<3
```

开发机在 `.streamlit/secrets.toml` 创建以下内容，填真实值但不要提交该文件：

```toml
[supabase]
url = "https://<project-ref>.supabase.co"
publishable_key = "sb_publishable_..."

# 只给一次性迁移脚本或管理员后端使用；正常应用请求不使用它。
secret_key = "sb_secret_..."

[openai]
api_key = "..."
```

旧的 `fitness.py` 已经会读取 `st.secrets` 里的 AI 配置，Supabase 配置也沿用同一机制。客户端每个 Streamlit session 单独创建，避免把某个教练的登录令牌保存在全局缓存中：

```python
from supabase import Client, create_client

def get_supabase() -> Client:
    return create_client(
        st.secrets["supabase"]["url"],
        st.secrets["supabase"]["publishable_key"],
    )
```

### 5.2 登录改造（必须先做）

删除/停止使用：

- `coaches` 表和 `verify_coach(username, password)`。
- `seed_default_coaches()`。
- 页面中的默认账号提示。

登录表单改为邮箱和密码，核心流程如下：

```python
def sign_in(email: str, password: str):
    client = get_supabase()
    result = client.auth.sign_in_with_password(
        {"email": email, "password": password}
    )
    st.session_state.supabase_access_token = result.session.access_token
    st.session_state.supabase_refresh_token = result.session.refresh_token
    st.session_state.coach_id = str(result.user.id)

def get_authenticated_client() -> Client:
    client = get_supabase()
    access = st.session_state.get("supabase_access_token")
    refresh = st.session_state.get("supabase_refresh_token")
    if not access or not refresh:
        raise PermissionError("请先登录")
    client.auth.set_session(access, refresh)
    return client

def sign_out():
    client = get_authenticated_client()
    client.auth.sign_out()
    for key in (
        "supabase_access_token",
        "supabase_refresh_token",
        "coach_id",
        "logged_in",
    ):
        st.session_state.pop(key, None)
```

在每次需要用户数据的页面调用 `get_authenticated_client()`；RLS 会使用其中的用户 JWT。不要用 secret key 创建该客户端，否则它会绕过 RLS。

初期可以由管理员在 Dashboard **Authentication → Users → Add user** 邀请教练。正式向外部教练开放邮箱确认、找回密码或邀请邮件前，配置自定义 SMTP；Supabase 默认 SMTP 仅适合开发且对收件人有限制，见 [SMTP 官方说明](https://supabase.com/docs/guides/auth/auth-smtp)。

### 5.3 数据查询改造范例

把 SQLite 的：

```python
c.execute(
    "SELECT id, name FROM members WHERE coach_id = ? ORDER BY id DESC",
    (coach_id,),
)
rows = c.fetchall()
```

改为：

```python
def get_members(coach_id: str):
    result = (
        get_authenticated_client()
        .table("members")
        .select("id,name,remaining_lessons,goal,last_training_date,ai_reminder,phone,note")
        .eq("coach_id", coach_id)
        .order("id", desc=True)
        .execute()
    )
    return result.data
```

插入会员：

```python
def add_member(coach_id: str, name: str, remaining_lessons: int, goal: str):
    return (
        get_authenticated_client()
        .table("members")
        .insert(
            {
                "coach_id": coach_id,
                "name": name,
                "remaining_lessons": remaining_lessons,
                "goal": goal,
            }
        )
        .execute()
        .data[0]
    )
```

更新时仍保留 `.eq("coach_id", coach_id)` 与 `.eq("id", member_id)`；RLS 是第二道防线而不是替代正确查询条件：

```python
(
    get_authenticated_client()
    .table("members")
    .update({"phone": phone, "note": note})
    .eq("id", member_id)
    .eq("coach_id", coach_id)
    .execute()
)
```

需要创建训练记录和动作明细的地方，不能再靠 SQLite 跨语句事务与 `lastrowid`。可先插入 `training_sessions` 并从返回的 `.data[0]["id"]` 取得 ID，再批量插入 `training_session_exercises`。为了让“保存记录、扣课时、写动作”原子化，正式版最好创建一个 Postgres RPC 函数，在一个数据库事务内完成这些操作。

### 5.4 照片上传与读取改造

替换 `save_uploaded_training_photos()` 对本地 `Path.write_bytes()` 的调用：

```python
import mimetypes
import uuid

def upload_training_photo(coach_id, member_id, session_id, uploaded_file):
    extension = Path(uploaded_file.name).suffix.lower()
    if extension not in {".jpg", ".jpeg", ".png"}:
        raise ValueError("只允许 JPG、JPEG、PNG")

    object_path = (
        f"{coach_id}/{member_id}/{session_id}/{uuid.uuid4().hex}{extension}"
    )
    content_type = mimetypes.guess_type(uploaded_file.name)[0] or "image/jpeg"
    client = get_authenticated_client()
    client.storage.from_("training-photos").upload(
        object_path,
        uploaded_file.getvalue(),
        {"content-type": content_type},
    )
    return (
        client.table("training_session_photos")
        .insert(
            {
                "coach_id": coach_id,
                "member_id": member_id,
                "session_id": session_id,
                "object_path": object_path,
                "original_filename": Path(uploaded_file.name).name,
            }
        )
        .execute()
        .data[0]
    )
```

signed = (
    get_authenticated_client()

在 `fitness.py` 中完成以下替换并逐项测试：

## 6. 从现有 SQLite 导入数据

### 6.1 推荐导入顺序

严格按依赖顺序导入：

1. Auth 用户和 `profiles`，并形成旧 `coaches.username` → 新 UUID 的映射。
2. `exercise_library`。
3. `members`。
4. `lesson_plans`、`training_logs`、`body_measurements`、`training_sessions`、`ai_analysis_reports`。
5. `training_session_exercises`、`training_plans`、`training_plan_exercises`。
6. Storage 图片对象，再导入/更新 `training_session_photos.object_path`。

保留旧的 bigint `id` 可以大幅降低关联表迁移难度；本 schema 使用 `generated by default as identity`，因此可信的一次性导入可显式插入旧 ID。全部导完后，执行第 6.4 节的 sequence 校正。

### 6.2 先创建账号与映射表

旧数据库只有用户名和明文密码，不含邮箱。创建一份仅留在本机、不提交 Git 的 `coach_emails.json`：

```json
{
  "wenwen": {"email": "wenwen@example.com", "nickname": "文文教练"},
  "numb": {"email": "numb@example.com", "nickname": "Numb 教练"}
}
```

一次性迁移脚本用 **secret key** 调用 Admin API 创建用户（该 API 仅能在受信任服务器/本机运行）。每位用户设置临时随机密码，随后要求其重设。Supabase 的 Admin create user 能创建已确认用户，参考 [官方 Python API](https://supabase.com/docs/reference/python/auth-admin-createuser)。

```python
# 仅迁移机执行；不要放入 Streamlit 应用，更不要提交 secret key。
import json
from supabase import create_client

admin = create_client(SUPABASE_URL, SUPABASE_SECRET_KEY)
coach_map = {}

for old_username, person in json.load(open("coach_emails.json", encoding="utf-8")).items():
    response = admin.auth.admin.create_user(
        {
            "email": person["email"],
            "password": create_one_time_random_password(),
            "email_confirm": True,
            "user_metadata": {
                "username": old_username,
                "nickname": person["nickname"],
            },
        }
    )
    coach_map[old_username] = str(response.user.id)

json.dump(coach_map, open("coach_id_map.json", "w", encoding="utf-8"), ensure_ascii=False)
```

如果 Auth 用户是从 Dashboard 手工创建的，执行下面 SQL 导出映射并存为 `coach_id_map.json` 即可：

```sql
select p.username as old_username, p.id as new_coach_uuid
from public.profiles p
order by p.username;
```

### 6.3 编写一次性导入脚本

建议新建一个不提交的 `migrate_sqlite_to_supabase.py`，使用 secret key 运行。脚本的核心原则：

- 每次从 SQLite 读一张表；不要用 `sqlite3 .dump` 直接导入 PostgreSQL。
- 任何含 `coach_id` 的行都改为 `coach_map[row["coach_id"]]`。
- 原字符串日期可直接传入 ISO 格式；空字符串日期转为 `None`。
- 批量 `insert(rows)`，每批 100～500 条；发生错误时记录具体表和 ID 并停止。
- 导入前后都记录每表数量；不要以“脚本跑完”代替校验。

核心转换例子：

```python
def migrate_members(sqlite_conn, admin_client, coach_map):
    sqlite_conn.row_factory = sqlite3.Row
    rows = sqlite_conn.execute("select * from members order by id").fetchall()
    payload = []
    for row in rows:
        payload.append(
            {
                "id": row["id"],
                "coach_id": coach_map[row["coach_id"]],
                "name": row["name"],
                "remaining_lessons": row["remaining_lessons"] or 0,
                "goal": row["goal"] or "",
                "last_training_date": row["last_training_date"] or None,
                "ai_reminder": row["ai_reminder"] or "",
                "phone": row["phone"] or "",
                "note": row["note"] or "",
                "created_at": row["created_at"] or None,
            }
        )
    for start in range(0, len(payload), 200):
        admin_client.table("members").insert(payload[start:start + 200]).execute()
```

迁移照片时，将 `uploads/training_photos/...` 的实际文件上传到新对象路径，并把数据库中的 `file_path` 改写为 `object_path`。不存在的本地文件必须记录为异常清单，不能悄悄创建空照片记录。

完成所有导入后立即撤销/旋转迁移机所用 secret key，或至少确保它未出现在脚本、终端日志和 Git 历史中。

### 7.2 使用 Streamlit Community Cloud

## 8. 上线后的运维清单

- **数据库备份**：定期做离线逻辑备份。免费层尤其应自行导出；注意数据库备份不包含 Storage 图片对象。详见 [Supabase Backups](https://supabase.com/docs/guides/platform/backups)。
- **Storage 备份**：单独定期下载/同步私有 Bucket 的照片；不要误以为 DB backup 会带走对象文件。
- **用户管理**：只通过 Supabase Auth 创建、禁用和重置教练账号；永远不再手动维护密码列。
- **最小权限**：应用以 publishable key + 用户会话运行；secret key 不部署到普通 Streamlit app。
- **监控**：查看 Streamlit 部署日志与 Supabase Logs，重点关注认证失败、RLS 拒绝、数据库错误、Storage 上传失败。
- **Schema 变更**：每次新增字段或表，把 SQL 保存为带日期的 migration 文件，先在测试 Supabase 项目验证，再进入生产。
- **定期演练恢复**：每季度从备份恢复到一个测试项目，并确认至少能登录、读取会员、查看训练记录和照片。

# 备份与恢复

## 迁移前（必须确认后再 execute）

1. 停止 Streamlit 写入，确认没有其他进程在修改数据库/照片。
2. 将 `ai_coach_os.db` 和完整 `uploads/` 复制到明确命名的离线备份目录，保留时间与 SHA256 清单。SQLite 使用 WAL 时不能只复制正在写入的主文件；使用 SQLite backup API 或停止应用并确认 checkpoint 后再复制。
3. 在备份副本执行 `PRAGMA integrity_check`，并核对训练数量、会员课时、照片数量和文件可读性。
4. 保留旧代码版本、迁移映射（含敏感关联，安全保管）和阶段报告。不要提交备份/映射到 Git。

本次阶段 A 没有替用户复制、删除或覆盖原始数据库、照片，也没有创建远程备份；迁移前需用户确认备份确实完成。

## 上线后的三类备份

- 代码：经审查后提交 GitHub，给已验收版本打标签。
- 数据库：使用 Supabase 支持的数据库备份/dump 方式，记录 schema、public 业务数据、所需 Auth/角色恢复流程；密码和连接串通过环境变量/安全配置输入，不写命令日志或仓库。恢复 Auth UUID 是 coach_id 外键成立的前提。
- Storage：**数据库 dump 不等于图片备份**。单独下载/同步 `training-photos` 对象字节和对象路径清单，记录 SHA256。先验证数据库照片 metadata 与对象逐一对应。

不要把 signed URL 当备份内容，它会过期。存储的是 object_path 和实际文件。

## 恢复演练

在全新隔离测试项目恢复，禁止覆盖生产。先核对 Auth UUID，再恢复 schema/RLS、业务数据、identity sequence，最后恢复私有 bucket 对象和 Storage 策略。验证所有表行数、课时、FK、文件哈希和两用户隔离；通过后才切流量。

## 迁移失败 / 孤立照片

停止写入，保留本地数据及本次日志。脚本只插入缺失行、拒绝冲突行；修正配置/数据需人工确认，不自动删除任何业务数据。Metadata 失败而上传成功的对象，可由重新执行验证复用。

孤立对象对账：用管理员离线列出 bucket 对象与 public.training_session_photos.object_path 比对，先生成只读差异清单。只有确认备份、保留期和明确对象路径后才考虑删除，不自动清空 bucket。

## 回退 SQLite

阶段 D 之前，默认 sqlite 未变。上线后若要回退，先冻结云写入并导出新增数据；旧本地 SQLite 不包含上线后新数据，不能直接切回而宣称零数据丢失。恢复到独立目录/数据库副本，核对后再启动旧版本。
